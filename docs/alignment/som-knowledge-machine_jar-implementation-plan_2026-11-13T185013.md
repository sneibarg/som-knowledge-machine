# SOM-KM JAR implementation plan

Build the existing Clojure code in `som-knowledge-machine` as a thin Maven library and consume it from `som-nlp-service` on Java 17. This is the packaging step from the [SOM-KM API architecture proposal](som-knowledge-machine_2026-11-13T184038.md). It ends when the packaged Spring Boot application can call the engine in process. The REST API and standalone service cutover are later work.

## 1. Build and install the library in som-knowledge-machine

- **`deps.edn`.** Add a build-only `:build` alias for `io.github.clojure/tools.build`, pinned to a Maven Central release such as `0.10.14`. Set `:ns-default build` and keep the existing runtime dependencies and CLI aliases. The library POM should derive its dependencies from the project basis with no build or test aliases. It should currently declare `org.clojure:clojure:1.12.6` and `org.clojure:data.json:2.5.2`, which the packaged standalone adapter uses. [tools.build release and Maven coordinates](https://github.com/clojure/tools.build#release-information)
- **New `build.clj`.** Add `jar` and `install` tasks. Use a single set of coordinates, proposed as `org.springy.som:som-knowledge-machine:0.1.0-SNAPSHOT`. This version identifies the port artifact. The engine's reported KM version remains `2.5.45`. Stage `src/som/km/**/*.clj` under `som/km/` in a clean `target/classes`, and copy the root `LICENSE` verbatim to `META-INF/som-knowledge-machine/LICENSE`. Use `write-pom` and `jar` to produce dependency metadata and `target/som-knowledge-machine-0.1.0-SNAPSHOT.jar`. The artifact contains the runtime namespaces and license. Tests, Lisp reference sources, build code, and dependency JARs stay outside it. Clojure loads the packaged namespaces at runtime through `require`. Start with this source-JAR layout and consider ahead-of-time compilation only if packaged runtime testing identifies a concrete need. [Clojure source library build guide](https://clojure.org/guides/tools_build#_source_library_jar_build)
- **`src/som/km/license.clj`.** Read `META-INF/som-knowledge-machine/LICENSE` as a UTF-8 classpath resource first, then use the existing source-tree fallback for the CLI checkout. This is the one proposed engine-side packaging adjustment. The canonical text stays in the root `LICENSE`, and `som.km.interpreter` continues calling the same license function. The resource lookup is specific to the license. Knowledge-base loads, reloads, saves, and trace files continue using their existing filesystem paths and formats. Relative command paths resolve against the running process's working directory.
- **Local verification.** On the project JDK, run `clojure -M:test`, `clojure -T:build jar`, and `clojure -T:build install`. Let `install` build the JAR and install it with the generated POM via `clojure.tools.build.api/install`. Check that both repos use the same Maven local repository, especially if Maven settings override its location. Inspect the JAR with `jar tf` and verify the embedded POM and full license. [tools.build install API](https://clojure.github.io/tools.build/clojure.tools.build.api.html#var-install)
- **SOM-KM documentation.** In the implementation change, document the commands and artifact coordinates in `README.md`, record the JVM library boundary in `docs/reference/Architecture.md`, and add the packaging step to the migration notes and index. This step introduces no new Lisp forms.

## 2. Import and call the library in som-nlp-service

- **`pom.xml`.** Add a normal Maven dependency on the SOM-KM coordinates and let the generated POM resolve Clojure and data.json. Check the resolved versions with `mvnw.cmd dependency:tree` in case the Spring BOM or another dependency mediates them. For CI, deploy the library JAR with its generated POM to the configured Nexus snapshot or release repository, then confirm that the consumer's Maven settings can resolve the hosted artifact from a clean local repository. The application's existing `distributionManagement` names publication destinations. Dependency resolution uses the repositories and mirrors in the consumer's effective Maven configuration. [Maven deploy-file documentation](https://maven.apache.org/plugins/maven-deploy-plugin/deploy-file-mojo.html)
- **`src/main/java/org/springy/som/nlp/km/internal/`.** Add a small Java bridge that uses `clojure.java.api.Clojure` to require `som.km.engine` and resolve `status`, `session`, and `evaluate` once. The JVM call path starts at the engine namespace. Keep Clojure types behind the bridge. Create a session with `session` and pass its keyword-keyed state map to `evaluate`. When a result carries a knowledge base, carry both returned `:kb` and `:query` to the next call. The caller owns that state. As a JVM interop check, this step needs only local calls from trusted test code. HTTP routes and term-to-JSON conversion belong to the API step. [Clojure Java API](https://clojure.github.io/clojure/javadoc/clojure/java/api/Clojure.html)

## 3. Verify the consumer on Java 17

1. Run the Spring Maven wrapper with `JAVA_HOME` set to the project JDK. Add a bridge test that verifies engine status, evaluates `(1 + 2)`, and stores a fact and reads it back through successive calls using returned state. Verify a fresh session cannot see that fact.
2. Exercise the existing `save-kb` and `load-kb` commands with an absolute path in a test-owned temporary directory. Load the saved text into a fresh session and read the fact back. Run the existing Clojure suite to retain coverage of the REPL, standalone HTTP adapter, and load and save behavior.
3. Package the Boot application. Use a test-only smoke entry point with Boot's nested-JAR layout to call the bridge from `java -jar`, with no SOM-KM checkout on the classpath and a working directory outside both repositories. This catches namespace and context-classloader issues that a flat Maven test classpath can miss. Verify the engine answers a query and `(license)` returns the full SOM-KM notice. Keep the smoke entry point out of the production API. [Spring Boot executable JAR restrictions](https://docs.spring.io/spring-boot/specification/executable-jar/restrictions.html)

Completion requires a reproducible producer build and a consumer that resolves and runs the published artifact. The coordinates and source-JAR layout are proposals. Nexus resolution and nested-JAR startup still need to be exercised during implementation.
